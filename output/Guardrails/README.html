General Description

Tool to guard against misbehaviours by classifying generated content (model).

GuardRails Tool

A guardrails model is a dedicated component designed to ensure that a Large Language Model (LLM) behaves safely, reliably, and in alignment with organizsation requirements, policies, and ethical standards. Unlike the core LLM, whose primary function is to generate text or perform reasoning, the guardrails model operates as a protective layer that monitors and constrains the LLM’s outputs and interactions. It takes the form of a classifier model associated with a set of restrictive rules.

Guardrails are necessary to guard against misbehaviours because modern LLMs are highly capable but inherently probabilistic systems: they generate outputs based on patterns learned from data rather than explicit programming. As a result, they can inadvertently produce content that is harmful, biased, or in violation of legal, ethical, or domain-specific requirements. In safety-critical or regulated environments, such as those falling under the EU AI Act, these risks must be mitigated systematically. Guardrails also help ensure responsible use of computational resources by aligning LLM behaviour with an organisation’s intended purposes and policies. This becomes increasingly important as automation workflows expand and LLM-driven agents are chained together, since harmful or unsafe outputs can propagate through multiple steps if not intercepted early.

Tool Design

Overview

A guardrails model serves several key functions:

  • Safety and Compliance: It helps prevent the model from producing content that is unsafe, discriminatory, inappropriate, or in breach of legal and ethical guidelines (e.g., GDPR, AI Act obligations, sector-specific regulations).
  • Policy Enforcement: It implements project-specific behavioural constraints, ensuring that the LLM follows predefined rules, roles, or usage boundaries.
  • Quality Control: It monitors for errors, hallucinations, or low-confidence outputs, enabling corrective behaviours such as refusal, re-querying, or flagging outputs for human review.

The GuardRails model developed in the project serves as a dedicated safety layer for large language models. Its purpose is to identify and intercept unsafe, policy-violating, or jailbreak-related content across the different stages of an LLM interaction pipeline. The model is structured around three main types of inputs:

  1. User Messages (Prompts)
    GuardRails analyses incoming user prompts to detect attempts to circumvent system instructions, trigger harmful behaviour, or introduce content that violates safety or usage policies. This includes both explicit jailbreak attempts and more subtle forms of prompt manipulation.
    The classifier assigns an initial safety label (e.g., safe, harmful, jailbreak attempt) and can be used to block or re-route prompts before they reach downstream LLM components.

  2. Model Responses
    Outputs generated by the base LLM are evaluated to ensure they remain within acceptable safety boundaries. The guardrails model distinguishes between safe content, harmful content, and model refusals, enabling a clearer understanding of the model’s behaviour and its ability to apply its own internal safety mechanisms.
    This component supports monitoring and logging of responses, allowing systems to enforce appropriate handling strategies such as redaction, re-generation, or escalation.

  3. External or Retrieved Content
    When external documents, search results, or retrieved knowledge are incorporated into an LLM workflow, GuardRails assesses this content before it is used in generation steps. This ensures that harmful or inappropriate material does not propagate through multi-step agent pipelines or contaminate contextual information provided to the model.

The GuardRails framework is designed to support more advanced safety and compliance features as the project evolves. These include:

  • Dynamic, policy-aware classification
    The system architecture allows for the guardrails model to be aligned with variable or domain-specific policies. This includes adapting classification to different organisational rules or regulatory requirements without altering the underlying LLM.

  • Jailbreak detection relative to system instructions
    Future iterations will strengthen the model’s capacity to identify whether a user message or model response attempts to deviate from or override the original system prompt or operational constraints. This moves beyond static lists of jailbreaks toward contextual jailbreak detection.

  • Multi-label content categorisation
    Beyond a binary safe/harmful judgements, the model can be extended to categorise content according to specific types of policy violations (e.g., hate speech, self-harm, disallowed personal data, extremist content). This enables more granular tracing of safety issues and supports targeted mitigation strategies.

Architecture

The Guardrails architecture is designed to train and deploy a safety-aligned LLM that can classify text associated with any stage of an LLM workflow: user prompts, model responses, and retrieved/tool content. The approach focuses on fine-tuning a base model (Qwen3 family models) on curated public datasets to produce a unified safety classifier. This section describes the architecture as implemented in Year 1, with placeholders for design elements that will be finalizsed in later phases.

  1. Dataset Ingestion and Consolidation
    The architecture begins with the collection and harmonisation of publicly available safety-related datasets. These datasets include examples of harmful prompts, adversarial harmful prompts (e.g. jailbreaks), safe prompts, harmful outputs, safe outputs, and explicit refusals. All examples are standardised into a minimal schema. They are combined into a single training corpus that reflects the two core interaction roles:

    • User prompts (messages directed at the LLM).
    • Model responses (LLM outputs), including refusals.
    • Retrieved content used by agents or retrieval-augmented systems.

  2. Model Fine-Tuning Module
    The core of the architecture is a fine-tuned version of an open weights LLM (currently in the Qwen3 family), following a supervised instruction tuning approach. We've adopted a Parameter Efficient Finetuning approach based on the recipe we created for Task 2.5. The consolidated dataset is used to train the model to predict one of 2 labels: safe, harm.
    In the current version, the model is trained with a fixed generic guardrails system prompt. The goal is to leverage the base model’s language understanding capabilities to produce a classifier that is robust across the three content types and capable of generalizing to previously unseen harms or jailbreak attempts. The future goal is to allow for user-defined policies implemented through the system prompt. The resulting model acts as a unified classifier capable of screening text at multiple points throughout a system.

  3. Deployment and Inference Layer
    Once fine-tuned, the model is expected deployed behind an OpenAPI compatible endpoint served via a standard LLM serving framework such as vLLM or Ollama, altough it is possible to use other interfaces for LLMs including code libraries such as Huggingface transformers.

  4. Design Rationale and Extensibility
    The architecture emphasizses:

    • Consistency — the same classifier is used for prompts, responses, and retrieved content.
    • Adaptability — new datasets and new content categories can be added without redesigning the system.
    • Future readiness — the architecture supports future extensions planned for later project phases, designed so they can be integrated without too many structural changes:
      • variable policies or domain-specific policy profiles through changes in the guardrails system prompt.
      • contextual jailbreak detection relative to the base LLM system prompt.
      • multi-label classification (e.g., harm categories based on specific policy types).
      • integration with pipelines requiring multi-turn classification.
