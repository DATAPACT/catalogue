LexAlign Decision Flow Schema

Object-oriented view of how editable decision graphs become executable question flows, and how each run records state, obligations, warnings, and provenance.

1. Author

A tenant-owned ComplianceFlow stores editable nodes, alternatives, ordered edges, conditions, actions, and a start node.

2. Publish

Validation checks graph consistency, then publishing compiles the graph into a runtime RegulationFlow and immutable snapshot.

3. Execute

The evaluator traverses Question payloads against a fact object and accumulates a StateObject for reports.

Core Associations

ComplianceFlow 1 has 0..* FlowNode, FlowEdge, ComplianceFlowSnapshot

Publishing Transform

ComplianceFlow draft
  -> validate_flow_payload(payload)
  -> compile_flow_to_runtime_definition(payload)
  -> RegulationFlow.definition_file with { questions: [...] }
  -> ComplianceFlowSnapshot.schema_json
  -> selectable runtime RegulationFlow
FlowEdge(condition, actions, target_node_id)
  -> RoutingInstruction line
  -> "<condition> -> 'st:<status>' + 'ob:<obligation>' + 'id:<next>'"

Execution Semantics

  1. The platform starts a selected DerivationFlow or RegulationFlow for a workspace.
  2. The evaluator loads runtime Question objects from definition_file.
  3. Each question is answered from trusted rules or an LLM workflow.
  4. Answers are normalized to the question schema.
  5. The action resolver picks the first matching routing instruction.
  6. Effects update StateObject.statuses and StateObject.obligations.
  7. Provenance records the response, action, effects, and response metadata.
  8. Traversal follows next_question until END or warning accumulation.
  9. Multi-true radio answers create branches that are evaluated and merged.

Validation Rules

  • A flow must include nodes and a valid start_node_id.
  • Node types are single_select, multi_select, info, and end.
  • Decision nodes require alternatives.
  • Node ids, alternative ids per node, and edge ids per flow are unique.
  • Edges require known sources and valid targets or END.
  • Edge priority must be a non-negative integer.
  • Non-terminal authoring nodes require at least one transition edge.
  • Condition clauses must reference known alternatives, nodes, or status keys.
